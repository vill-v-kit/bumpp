# --dry-run 语义与效应边界结构:预演与执行同路

`--dry-run`(bump 默认命令与 release 子命令共用)给出发版前的执行计划预览。本 ADR 记录两条决策:预览的**语义**(校验、token、交互、退出码的口径)与**结构**(预览如何获得与真实执行一致的行为)。

## Decisions

### 语义

- **前置校验硬失败 exit 1,与真实执行逐字节一致。** tag 存在性、changelog 版本节存在性、版本号合法性等只读前置校验照常走,失败按真实执行的报错文案退出 1——dry-run 因此可直接当 CI 预检门禁(`vbumpp release $V --provider $P --dry-run` 作为发布前检查步骤,失败即阻塞流水线)。预览不是"尽力而为的提示",而是与真实执行同一判定。
- **token 缺失只警告不报错(exit 0),存在则报告来源。** token 走与真实执行同一解析链(token 存储 → 各家环境变量 →(仅 github)`gh auth token`),命中时报告具体来源(token store / 环境变量名 / gh CLI);未命中降级为一行警告(复用真实执行的报错文案,仅降级不改措辞),预览照常输出。token 是发布时刻的运行时凭据而非预检对象——预检阶段没有 token 是常态(CI 往往到真正发布那步才注入),硬失败会让 dry-run 失去"无凭据也能看计划"的价值。
- **零副作用保证:零写盘、零 git 写操作、零网络。** 全部副作用(文件写盘、git commit/tag/push、scripts 与 install/execute 的子进程、平台 Release 的 HTTP——含 gitlab 的 GET project id)在效应边界被拦截,改为计划行。dry-run 全程不打印任何 success 行(✔),开头标识 dry run,与真实执行的成功收尾明确区分。
- **版本选择交互保留,`Bump?` 确认跳过。** 版本选择菜单与 custom 输入照常弹(不定版本则无计划可预览——preview 的内容依赖已确定的新版本);但零写盘无需二次确认,`Bump?` 这一步跳过(经配置注入 `confirm=false` 在流水线内生效,流水线本身不感知预览分支)。
- **逐行人类可读输出,按真实执行序。** 逐文件预演判定(`update → {新版本}` / `up-to-date` / `missing`)、当前版本及其来源、新版本、将写盘文件、将执行的脚本与命令文本(scripts 三槽位 / install 实际命令 / execute)、git 动作完整文本(`%s` 替换后的 commit message / tag 名 / push 序列)、changelog 全文预览、`--provider` 时的平台 Release 预览(provider / host / owner/repo / tag_name / prerelease / body 全文)与 token 来源报告。

### 结构

- **预览与真实执行骑同一条流水线,副作用在统一效应边界收口。** bump/release 流水线的全部副作用已收口为 `Effects` 四个原语(文件写盘、子进程执行、平台 HTTP 收发);真实执行注入 `RealEffects`,dry-run 注入一个记录型实现——同一套配置合并、glob 收集、版本读取与计算、逐文件判定、git 动作格式化、changelog 生成、Release 请求构造全部照走,只有副作用在边界被拦截为计划条目。**预览保真由结构保证**:判定、计算、格式化只有一份实现,预览看到的必然就是真实执行会做的,不依赖人工同步。
- **逐文件预演判定复用只读判定段。** 逐文件更新已拆为「判定段(只读:`plan` 产出更新计划)」与「写盘段(消费计划经边界执行)」两段;dry-run 的三态判定行(update / up-to-date / missing)与真实执行的逐文件判定是同一代码段的产物,不是另写一份"预览版判定"。
- **token 与 Release 预览的明文不出 release 模块。** dry-run 的 Release 预览由 release 模块内部完成宽容 token 解析(缺失不报错)+ dispatch + 装配,明文 token 不跨模块边界;拦截到的请求行(如 gitcode 的 query 注入形态)经与报错同一脱敏原语(`[redacted]`)处理后才进入计划。

## Alternatives considered

- **复制一套预览流水线(被否决)。** 另写一份"预览版"的 bump/release 流程,在里面逐点替换成"只打印不执行"。被否决:两份逻辑必然漂移——真实流程后续任何行为修正(校验顺序、格式化细节、边界条件)都要记得同步到预览副本,漏一处预览就在说谎,而 dry-run 的全部价值恰恰在于"看到的就是会发生的"。保真必须由结构(同一条流水线、副作用一处收口)保证,不能靠纪律。
- **token 缺失报错(被否决)。** 与校验失败一视同仁 exit 1。被否决:token 是发布时刻的运行时凭据,预检阶段没有 token 是常态;硬失败会让 dry-run 在 CI 预检、本地无凭据预览两类主场景都不可用。降级为警告既保留了提示(用户知道发布时该配 token),又不阻塞计划预览。
- **无人值守时连版本选择也跳过(被否决)。** dry-run 在非交互场景自动挑一个版本(如 latest hint)直接出计划。被否决:预览的内容(逐文件判定、changelog、Release body)全部依赖已确定的新版本,不定版本就没有有意义的计划;静默替用户选一个版本会让预览对应不到用户真实想发的那次。保留版本选择菜单,让用户像在真实发版一样定下版本,预览才"所见即所得"。

## Consequences

- dry-run 可当 CI 预检门禁:校验失败 exit 1 与真实执行一致,流水线直接用它做发布前检查。
- 预览行为的维护成本趋近于零:真实流程的行为修正自动反映到预览,不存在两份逻辑的对账负担;新增副作用点只需归入 `Effects` 边界即同时被真实与预览覆盖。
- 无 token 的本地/CI 也能完整预览计划与 Release 目标,token 缺失只是一行提示。
- 交互语义与真实发版一致(选版本)但无冗余确认(零写盘不二次问),预览的交互负担最小。
